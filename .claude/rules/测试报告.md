# 测试报告编写规则（作用域：仅 `docs/测试报告/`）

本规则**只在处理 `docs/测试报告/` 下的文件时生效**；处理其他路径的文件不受本规则约束。

## 一、用户言语转写原则（核心）

- 用户的裁决、指示、反馈等内容一律以**语义化的书面语转写**后入账，**不得把原话原封不动地写进报告**——口语措辞、语气、助词、句子形态均不保留。
- 报告要留的是**决策本身**：选了哪种处置、口径边界在哪、由谁承接；说话的方式与语感没有记账价值，对账靠日期、提交号与章节锚。
- 引号仅用于**逐字引用客观字符串**：代码符号、校验消息文案、断言文本、命令及其输出片段等；不得用引号包裹转写的用户口语。
- 书写形态示例：
  - ✗ `用户裁决"修了吧"` → ✓ `经用户裁决修复（2026-10-09，提交 \`xxxxxxx\`）`
  - ✗ `用户裁决"返回null吧"` → ✓ `经用户裁决：空白值一律归一返回 null`
  - ✗ `用户裁决"采用这个方案修改，只剪裁首让尾巴落入守卫"` → ✓ `经用户裁决采纳该方案：键段只裁首部，尾部空段落入既有守卫拒收`
  - ✗ `用户裁决原话："目前测试覆盖率已经76%了，达到80%即可……"` → ✓ `裁决要点：覆盖率目标由 0.90 改定为 0.80，后续阶段相应收敛`

## 二、处置条目的书写口径

- 修复类：`已修（经用户裁决修复，yyyy-MM-dd，提交 \`xxxxxxx\`）` + 修法概述；
- 不修类：`经用户裁决不修，产品代码保持现状`，钉住用例转行为锚等连带处置照实记录；
- 移交类：`经用户裁决移交 docs/优化清单/ 专项承接`，注明承接条目与出处；
- 多方案比选：只记**采纳的方案与其实质内容**（如"裁决采纳修法 A：……"），未采纳方案以一句概略保留即可；
- 涉边界口径的：把口径改写为规则化表述（如"合法下界含 1000 本身"），并落到判定 / 文案 / 断言的具体位置。

## 三、逐字引用例外

- 确有争议核对等需要逐字保存用户表述的：须经用户**明确点名**方可写入报告，并标注"经用户同意逐字引用"；默认一律走 §一 转写。

## 四、文体

- 报告正文统一使用技术文档书面语，叙述以事实与证据为主（日期、提交号、文件:行号、读数），不写过程性感慨、对话实录或聊天体口语。
- 报告内 §10.x 历史小节**只增补不改写正文**的既有惯例不变；本条只约束**新写入**的文字。

## 五、存量内容与提交口径

- 本规则**不追溯改写历史条目**：已入账的原话引语属既成的记账事实，维持现状；若需一次性转写清扫，由用户明确指示后单独落纯文档提交，不搭其他改动的便车。
- 报告入库 / 变更的提交说明用文档域模块名：`docs(测试报告): …`（承 CLAUDE.md §8）。

## 六、归档与冻结（2026-10-10 用户裁定固化）

- 测试程序收口后的报告整篇移入 `docs/测试报告/归档/yyyy-MM/`（按月建文件夹、取完成当月，与 `docs/优化清单/` 的归档口径一致）。现状：`2026-10-07-阶段0-2测试报告.md` 已居 `docs/测试报告/归档/2026-10/`。
- **归档内的测试报告不得修改**：后续任何批次（修复、下架、清理等）一律不得向其追加小节、翻正计数或补记处置——归档即历史终账，只读。测试程序存续期间（报告未归档）的随批回写照本规则前文口径进行；报告一经移入归档，回写通道关闭，须重开时由用户明确指示，且指示重开也不得改动归档内已成文的条目本身。
- 后续批次的账面事实（计数、归因、挂账）只登记在工作区文档与台账笔记中，不再落归档报告。
