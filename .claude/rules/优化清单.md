# 优化清单规则（作用域：仅 `docs/优化清单/`）

本规则**只在处理 `docs/优化清单/` 下的文件（含 `归档/`）时生效**；处理其他路径的文件不受本规则约束。

## 一、编写权限（最优先）

- **不得自行创建、自行扩项、自行编写优化清单内容——只有用户明确指定时才写**：主题、问题面、优化方向均以用户点名为准。
- 排查 / 裁决过程中发现值得优化的点：只在回复中**指出**（文件:行号 + 问题），由用户决定是否立项（同 CLAUDE.md §7 不顺手改的精神）。

## 二、立项与文件粒度

- 优化清单放 `docs/优化清单/`：**一文件一主题**，文件名简略描写主题（如 `HttpContent内存管理优化.md`）。
- 清单**不替代缺陷裁决**：缺陷的修 / 不修仍走 `docs/测试报告/` 台账 §5 的用户裁决流程；清单若源于某台账缺陷，头部"来源 / 定位"须注明并声明"不构成裁决"。

## 三、文件内部结构（固定框架）

1. **必含"优化状态"大节**，下设 **待处理** / **已处理** 两子节：
   - 条目立项即记入"待处理"（编号 / 项 / 优先级 / 立项日期）；
   - 条目完成后**整条移入"已处理"**，注明处理提交号与日期；**不得**在"待处理"里就地打勾留痕。
2. 正文必须列举三类内容：**目前的状况**、**存在的问题**、**优化建议**——
   - "状况"与"问题"可合并为一节（如"现状与问题"），须带代码锚（文件:行号）与核对日期；
   - "优化建议"以分项细则形态归入"处理方案"（见下）。
3. **最后一个大标题固定为"处理方案"**：优化建议分项细则、优先级、落地节奏归此节。
4. 其余节（背景、现状 / 问题等）置于"优化状态"与"处理方案"两节之间。

## 四、归档

- 某清单**全部条目完成**（"待处理"清空）后，整个文件移入 `docs/优化清单/归档/yyyy-MM/`，`yyyy-MM` 取**完成当月**；归档子文件夹按月划分。
- 归档后的清单只读不再改；同主题若再起二次优化，立新清单并在头部注明前篇（可指归档路径）。

## 五、溯源与提交口径

- 清单条目对账靠**文件 + 提交号**；与 CLAUDE.md §9 同源——台账编号与推进记录**不进 `src/main` 注释**。
- 清单入库 / 变更的提交说明用文档域模块名：`docs(优化清单): …`（归档搬移同样落提交）。
- 专项排查撞出新缺陷：HS 编号按台账"只增不迁"规则顺延。
